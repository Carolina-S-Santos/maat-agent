# Maat: an LLM-based agent for evidence-graded explanation of digital phenotyping data and depressive symptoms

This repository contains the code and materials for the article:

> Santos, C. S., Heckler, W. F., Schroeder, G. L., & Barbosa, J. L. V. *Maat: An LLM-Based Agent for Evidence-Graded Explanation of Digital Phenotyping Data and Depressive Symptoms.* Submitted to *Smart Health* (Elsevier).

Maat receives a 14-day passive-sensing history and an already-known, item-level PHQ-9 profile, and produces a structured qualitative explanation that grades each behavior-symptom link as strong, moderate, or weak support, flagging unsupported links separately. Maat does not diagnose or predict. In the article, two implementations of Maat (based on `gpt-4.1-mini` and `gemini-2.5-flash`) explained 28 cases derived from the StudentLife dataset, and two LLM judges (`gpt-4.1` and `gemini-3.1-pro-preview`) scored each explanation with a referenceless, ten-criterion rubric.

## What this repository contains

| Folder | Contents |
| --- | --- |
| `scripts/` | The full pipeline: daily feature extraction, PHQ-9 processing, window coverage, 14-day histories, LLM input cases, Maat generation, judge evaluation, and analysis |
| `prompts/` | The Maat prompt (`qualitative_prompt_v1.md`) and the judge prompt with the rubric (`qualitative_judge_prompt.md`) |
| `dictionaries/` | The behavioral feature dictionary and the PHQ-9 dictionary supplied to Maat and to the judges |
| `results/` | Aggregated results reported in the article: mean scores per criterion and implementation, and inter-judge agreement per criterion |

## What this repository does not contain

The StudentLife data and everything derived from it at the participant level are **not** included: the 28 input cases, the explanations generated by Maat, the judge outputs, and any file with participant identifiers or dates. These files derive directly from, or restate, participant-level StudentLife data, so they are not redistributed. You can rebuild the cases from the original dataset with the scripts in this repository.

## Requirements

- Python 3.10 or later
- API keys for OpenAI and Google Gemini (only for the generation and judging steps)

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env             # then fill in your API keys
```

## Getting the StudentLife dataset

Download the StudentLife dataset from its official page (https://studentlife.cs.dartmouth.edu/dataset.html), following its terms of use, and extract it into a `dataset/` folder at the root of this repository. The scripts expect this layout:

```
dataset/
├── sensing/
│   ├── phonelock/phonelock_u*.csv
│   ├── dark/dark_u*.csv
│   ├── activity/activity_u*.csv
│   ├── conversation/conversation_u*.csv
│   └── wifi_location/wifi_location_u*.csv
├── app_usage/running_app_u*.csv
└── survey/PHQ-9.csv
```

`dataset/` and `outputs/` are listed in `.gitignore`. Do not commit them.

## Running the pipeline

Run the scripts from the repository root, in this order. Each script writes its output to `outputs/`.

**1. Build and validate the daily behavioral features**

```bash
python scripts/build_daily_features.py
python scripts/validate_daily_features.py
```

The six modalities (phone-lock events, ambient darkness, physical activity, detected conversation, Wi-Fi-based location, and app usage) are aggregated into one value per participant and calendar day.

**2. Build and validate the PHQ-9 outcomes**

```bash
python scripts/build_phq9_outcomes.py
python scripts/validate_phq9_outcomes.py
```

**3. Build the 14-day windows and histories**

```bash
python scripts/build_phq9_window_coverage.py
python scripts/build_phq9_post_14day_histories.py
python scripts/validate_phq9_post_14day_histories.py
```

Because the StudentLife PHQ-9 file has no response dates, the post-term reference date is inferred as the participant's last day with sensing data, and the window covers the 14 preceding days. A window is valid when at least 13 of its 14 days have data (`--min-available-days 13`). With these settings, 28 of the 38 post-term responses yield valid cases.

**4. Build the dictionaries and the LLM input cases**

```bash
python scripts/build_llm_feature_dictionary.py
python scripts/build_llm_phq9_dictionary.py
python scripts/build_llm_input_cases.py
```

The dictionaries are also provided in `dictionaries/`. `build_llm_input_cases.py` writes the anonymized cases (`outputs/llm_input_cases.jsonl`) and a local mapping file between case identifiers and participants (`outputs/llm_case_id_map.csv`). Keep the mapping file private.

**5. Generate the explanations with Maat**

```bash
python scripts/test_llm_connection.py      # optional: checks that the API keys work
python scripts/run_llm_experiment.py
```

By default, this runs the two implementations evaluated in the article (`openai/gpt-4.1-mini` and `gemini/gemini-2.5-flash`) at temperature 0.0, as set in `.env`. Use `--limit 2` for a quick test.

**6. Evaluate the explanations with the LLM judges**

```bash
python scripts/run_llm_judge_evaluation.py
python scripts/analyze_llm_judge_results.py
```

The judges (`openai/gpt-4.1` and `gemini/gemini-3.1-pro-preview`) never receive the name of the model that produced each explanation. The analysis script writes the per-criterion means, the cross-family comparison (which excludes judgments where the judge and the implementation share a provider), and inter-judge agreement per criterion, both raw (exact match) and chance-corrected (Fleiss' kappa, which for two judges is equivalent to Scott's pi).

## Notes on reproducibility

- Temperature 0.0 reduces sampling variability but does not guarantee identical outputs from commercial APIs, whose models may change over time. Rerunning steps 5 and 6 may therefore produce results that differ slightly from those in `results/`.
- The inferred PHQ-9 reference date is an approximation. See the Limitations section of the article.
- The rubric scores are LLM judgments without human calibration. They describe judge-rated properties of the explanations, not clinical validity.
